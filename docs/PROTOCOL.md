# 客户端、专服与 API 兼容性

**本分支协议 16 尚未发布；运行中的发布服务与游戏包仍为协议 15 / 0.34。开发联调使用独立 8001 / UDP 27031 环境。**

唯一版本清单是 `client/protocol.json`。Godot 客户端和专服读取同一资源；API 镜像构建时复制该文件，发行 PCK 也包含它。

| 字段 | 当前值 | 更新规则 |
|---|---|---|
| `protocol` | `16` | 改变 RPC、输入、快照或其他不兼容网络语义时递增 |
| `content_revision` | `ash-valley-17` | 改变地图碰撞或需要各端一致的游戏资源/规则时更新 |
| `client_version` | `0.35.0-dev` | 人类可读发行版本；仅用于提示，不决定兼容 |

兼容要求前两个字段完全一致。客户端在登录前查询 `GET /protocol`，不兼容时显示升级提示；匹配 API 在签发票据前再次验证。Redis 票据存储协议和内容版本；专服消费票据时也检查绑定，错误版本不会烧掉正常票据。消费检查与删除在同一 Lua 脚本内执行。

协议 4 将跳跃、换弹、治疗、拾取、投掷和切枪迁移到通道 4 的可靠有序 RPC。它携带回合 ID、操作序号和操作时的视角；移动输入仍在通道 1 不可靠有序传输，服务器忽略其中的一次性操作字段。可靠操作按独立序号去重，旧回合/已死亡/非进行中状态拒绝；落后最新移动超过 120 个输入序号的积压请求丢弃。操作预算每秒恢复 10 次、最多积累 10 次，限流拒绝的序号也会被消费，不能稍后重放。游戏冷却和库存规则继续生效；可靠送达不代表在无弹药或冷却中强制执行。

协议 5 为可靠操作增加整数补给目标编号（无目标为 -1），并在可靠世界状态中同步补给余量。服务器只尝试该编号，重新检查回合、存活、距离、遮挡和容量；目标消失或无效时不会自动改拿旁边物品。客户端不能指定拾取数量或写入库存，操作序号去重仍覆盖补给请求。

协议 6 在角色快照中增加 `mags` 三整数弹匣数组，依次对应 AR/SG/SR；原 `m` 字段仍由当前弹匣派生。客户端复制整个数组，不能通过输入提交弹药数量。切枪只切换当前弹匣，换弹完成才从共享储备转移弹药。

协议 7 增加通道 4 可靠丢弃 RPC，携带回合、操作序号、物资类别及整数数量。与其他操作共用去重序号和预算；服务器验证数量与库存，并在权威位置生成或合并物资。

协议 8 将默认匹配和专服鉴权迁移至房间目录入口；票据绑定 room_id、instance_id 与 generation。旧单地址接口的票据不再用于 Godot 入场。

协议 9 在快照中增加 `zone_state`：当前圆心与半径、下一圈圆心与半径、阶段编号、收缩状态及阶段剩余秒数。专服决定圈位与时间，客户端仅显示当前阶段预告；原 `zone` 字段仍表示当前半径。

协议 10 为输入增加 `lean`（有限数值，范围 -1 至 1），并在角色快照同步服务器实际探身量；延迟补偿记录倾斜碰撞体的基点和旋转，使用局部坐标判定头部命中。

协议 11 增加可靠一次性 `smoke_throw` 输入、角色 `smokes` 库存、投掷物 `kind` 和通道 5 的权威烟雾快照（回合 ID、分批云团位置/年龄及完整存活 ID 集合）。物资种类 4 为烟雾弹。

专服启动时用服务密钥请求 `/internal/build/check`，成功后才监听 ENet 端口。不兼容或 API 不可用会导致进程非零退出，Docker 可按重启策略重试。API `/health` 同时提供数据库与协议版本。

修改清单后，重新构建并一起部署 API、专服和客户端：

```sh
docker compose up -d --build api game game2
./tools/package.sh
```

当前采用停服协调升级：应先等待现有对局结束，再执行部署并分发新客户端。这条命令本身不会等待对局结束。旧客户端会被明确拒绝；尚无多版本房间调度、自动补丁分发或无中断滚动升级。

版本声明是兼容性检查，不是二进制完整性证明，不能替代反作弊。允许恶意修改的客户端伪造版本字段，不应据此信任其游戏输入。

验证入口是 `tools/test_protocol.py`、`tests/protocol_client.gd` 和 `tools/test_protocol_server.py`。前两项需要运行中的本地 API，专服测试会启动临时不兼容进程并确认它没有开始监听。完整回归见 `tools/verify.sh`。

## 输入中断

专服超过 350 毫秒未收到有效的新序号移动包时，将移动、开火、疾跑、瞄准、侧身和蹲伏请求置为释放状态。站立仍受角色头顶碰撞约束。已经接受的可靠跳跃、换弹/治疗计时和已投出的投掷物继续运行。此机制不会断开 ENet，也不是断线重连；有效输入恢复后继续控制原角色。移动和可靠动作统一要求序号为 0–2147483647 范围内整数，武器选择必须为整数，非法包不能刷新有效输入时间。

## 协议 12：握把配件

角色快照新增 `grips` 与 `grip_slots`，物资种类 5 为握把。`grip_command(round_id, seq, weapon_index, attach)` 使用可靠通道 4，共享动作去重、过期判断和预算。客户端只能请求修改当前装备的武器；库存、动作忙碌状态及容量由服务器验证。旧协议客户端必须更新后联机。

## 协议 16：开发中的队伍状态

角色网络快照增加 `team`，对局快照增加 `mode`，`accepted` 与 `new_round` 可靠通知携带模式。房间匹配、心跳和票据消费均绑定 `solo | duo`。队伍由权威服务器分配，客户端输入不能提交队伍。组队其他功能仍在开发，当前不发行此协议。

开发协议 16 的倒地快照还包括 `downed`、`down_health`、`bleed`、`revive_target`、`revive_left`。存活但倒地与正式淘汰明确区分；拾取交互无物资目标时可请求扶起附近队友，继续使用通道 4 的动作去重与预算，扶起时间和结果全部由专服决定。

开发组队大厅接口：`POST /parties/ready` 只接受布尔 `ready`，两人准备后由队长调用 `POST /parties/reserve`。已预约队伍响应提供非秘密的 `reservation_id`；`POST /parties/reset` 需要构建信息和对应 `group_id`，用于在成员租约释放后保留队伍、撤销旧预约并清除双方准备状态。旧编号不能重置后来签发的新预约。票据仍仅按当前账号返回。
