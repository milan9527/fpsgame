# 房间目录与名额预留

当前已实现服务端目录接口与 Redis 原子预留。**Godot 默认匹配仍使用旧的单地址接口；专服心跳、客户端路由和第二个实际专服尚未接入，因此尚不能称为已完成多房间游戏。**

新接口：

- `POST /internal/rooms/heartbeat`：专服密钥鉴权，报告房间编号、进程实例 UUID、回合 generation UUID、递增 revision、地址/端口、容量、阶段和已接纳玩家 UUID 列表。房间有效期 12 秒；集成时建议每 2 秒报告一次。
- `POST /matchmaking/rooms/join`：账户 JWT 鉴权。可指定房间，也可自动选择；只分配版本兼容、仍存活、处于 waiting/lobby 且有余量的房间。返回具体地址、端口、房间绑定和 45 秒票据。
- `POST /internal/rooms/tickets/consume`：专服密钥鉴权，按房间、实例和回合绑定一次性消费。错误房间不会烧掉正常票据；房间失效、已开始或回合变化时拒绝入场。

容量计算包含已确认玩家和未过期预留。分配、用户占位和票据创建在同一个 Redis Lua 操作中完成。消费票据后，预留仍占容量，直到心跳确认该玩家或 45 秒到期，防止“票据已消费、玩家尚未报告”期间超卖。

每个用户只能持有一份新目录预留或活跃房间占位。已确认用户随心跳刷新 15 秒占位，断开后从下一次心跳移除。新回合清理上回合未确认预留；旧回合票据无法跨回合使用。失联时可能需要等待剩余占位到期，尚无取消、重连或会话迁移接口。

同一房间仍存活时拒绝其他进程实例接管；revision 必须严格递增，过时报告不延长存活时间。实例内地址/端口/版本保持不变，同一回合容量保持不变；从 live/finished 回到候场必须更换 generation。报告不能抢占已属于其他房间的用户。

实现面向当前单 Redis 实例，Lua 使用同一实例的多个键；尚不支持 Redis Cluster 跨槽部署。旧单服接口暂未使用这些占位，因此新旧流程之间的跨入口互斥尚未生效，必须在游戏接入时迁移默认路径。

验证：

- `backend/tests/test_rooms.py` 在真实 Redis 上验证 20 个并发请求争抢两个各 2 人房间、同账户并发预留、票据绑定/一次消费、心跳确认前后容量、回合隔离、过时报告、过期边界及 HTTP 鉴权与模式校验。过期测试直接推进存储边界，并检查配置的 TTL，不代表长时间稳定性测试。
- `tools/test_room_api.py` 通过运行中的 HTTP API、真实 QA 账户和合成专服心跳验证两个不同地址的票据分配、用户占位与并发消费。它没有启动第二个 Godot 专服。

接下来需将 Godot 实例注册、回合状态、已接纳玩家与心跳连接，客户端改走新匹配入口，再部署第二个专服验证不同玩家进入不同回合以及故障剔除。
